# 转速数字"乱码/被撕开" —— 模拟渲染、根因与修法

对象: `src/lcd/lcd_ui.c`(大字转速) + 它的刷屏通路(`lcd_app.c` → `LCDHw.c` → SPI1 → ILI9341)
结论一句话: **数字不是"画错了", 是被"改得太勤 + 一次改得太大"撕开的** ——
转速读数每秒改 7~10 次、每次重刷 110x44 的整块(3.1ms), 而 ILI9341 没有 TE 同步线、
面板一直在自己扫屏: 这 3ms 里被扫过的行这一帧还是旧数字、下一帧才是新的, 于是屏上
是"两个数字拼在一起"。改法是把"改屏"变少、变小(见第 4 节), 并用第 2 节的模拟器
在 PC 上先把现象和效果都算出来再上板。

---

## 1. 先在 PC 上把屏"渲染"出来(模拟器)

新增 `tools/lcd_sim/`, 四件事都是照代码/数据手册来的, 不是示意画:

| 文件 | 干什么 | 忠实度依据 |
|------|--------|------------|
| `lvfont.py` | 解码 LVGL 的 `lv_font_montserrat_*.c`(bpp=4) | 按 `lv_font_fmt_txt.c` 的 PLAIN 分支逐句实现: `stride==0`(LVGL 自带 Montserrat 的 `font_dsc` 里没有 `.stride`)→ 位图是**连续位流**; nibble 经 `opa4_table` 映射; 基线 = `line_top + line_height - base_line` |
| `ui.py` | 按 `lcd_ui.c` 的坐标/字体/颜色建界面, 并复制 LVGL 的**标脏→部分刷新**语义 | ①`lv_label_set_text` 前后各标一次脏(旧框 ∪ 新框) ②`lv_obj_set_style_text_color` 在 LVGL 9 里**不去重**(`lv_obj_style.c` 的 `lv_obj_set_local_style_prop` 无条件 `lv_obj_refresh_style`) ③部分模式按 `lv_refr.c` 的 `get_max_row = data_size/(area_w*2)` 切条, 每一条一次 `LCD_SetWindows`+`LCD_WritePixels` |
| `panel.py` | ILI9341 的 GRAM + **自由扫描** + SPI1 写通路时序 | 面板某一"显示单元"在时刻 t 显示的内容 = t 之前最后一次扫过它时 GRAM 的值; 写通路按 `LCD_WritePixels` 的 256 像素/块(512B) + `spi_transfer` 每字节一次(含软复位)估算 |
| `sim.py` | 跑"当前固件"与"改后"两套策略, 输出撕裂统计 + 整屏 PNG + ASCII | 显示任务 5ms 一拍、LVGL 刷新 10ms(`LV_DEF_REFR_PERIOD`)、刷屏阻塞会把后面的节拍自然推后(与 `vTaskDelayUntil` 一致) |

跑法:

```
python tools/lcd_sim/sim.py --duration 8000 --axis both      # 出 out/report.txt + PNG
python tools/lcd_sim/layout_check.py                         # 布局回归: 改动只影响大字区
```

`layout_check.py` 的结论(已跑): 改前/改后两张屏只有 **1310 个像素**不同, 且**全部**落在
大字转速那一块(x 12..130, y 30..73) —— 拆数字位没有把标题/单位/滑条挤歪。

**关于扫描轴**: 从代码和原理图(`docs/hardware/HPM6EMotorV20.pdf` 的 J10)都看不出这块屏到底沿 x 还是
沿 y 扫(也没有 TE 引脚), 所以模拟器两个轴向都算。两种几何都会"把两个数字拼在一起",
结论不受影响, 只是裂缝方向不同(横口 / 竖口)。

## 2. 复现出来的东西(改前)

模拟 8 秒(SCLK 25MHz, 实测转速 ≈320RPM、末位噪声 σ≈3RPM, 面板 70Hz):

```
[axis=y current] 数字改写  7.5 次/秒 | 屏上数字每秒变 12.9 次 | 被撕开 96.0 ms (1.45%, 44 段)
[axis=y fixed  ] 数字改写  1.8 次/秒 | 屏上数字每秒变  4.0 次 | 被撕开 94.0 ms (1.35%, 14 段)
```

"被撕开那一瞬"屏上真正显示的数字带(ASCII, `#` = 亮像素; 上半截一个数字, 下半截另一个):

```
.#########.######..###########.......     ← 上半截: "320" 的笔画
.......###....###..##......###.......
......##......###..##.....###........
.....##.......###.........##.........
....######....###........###.........
........##.......###....##.......##..     ← 下半截: 另一个数字的笔画
.........##.....###.....##.......##..
.#......###...##........###.....##...
.#########..##########....#######....
...#####....##########.....####.......
```

这不是"字体画错", 也不是"某个字节丢了": 拿板子上的像素通路计数器(`LCD 5s: ... busy/tmo/abort`)
本该恒为 0 —— 撕裂完全发生在"面板自己在扫"这一侧。也就是说以前几次"查 SPI 丢字节"的
方向是查不到东西的, 因为数据一个字节都没丢。

### 机制核对(逐行级, 模拟器可复现)
把某一次改写前后每一行"显示的是旧值还是新值"数出来(数字带共 44 行, 其中墨迹 29 行):

```
t=2126.0ms  行==319: 44/44   行==322: 15/44   ← 面板还没扫到这条带, 屏上仍是旧的
t=2131.1ms  行==319: 38/44   行==322: 21/44   ← 面板正扫到数字中间: 上半截旧、下半截新 = 被撕开
t=2134.0ms  行==322: 44/44                   ← 面板扫完这一遍, 恢复成一个完整的新数字
```
也就是说: **同一位数字的字形被从中间切开**(不是"整块画面错位"), 与"数字被撕开"的观感一致;
每次撕开持续到面板把这条带扫完(≤ 一帧 ≈ 14ms)。

### 为什么改得这么勤
- `lcd_ui.c` 原来只要**整数**变一位就 `lv_label_set_text()` 重画大字(去重键就是整数)。
  实测转速的末位一直在动(编码器量化 + 电流纹波 + 1ms 采样), 于是每秒改 7~10 次。
- 顺带发现一个**时间基准 bug**: 节流写的是 `s_ui.tick_ms += APP_MAIN_LOOP_MS`(该宏 = 1),
  而显示任务其实是 5ms 一拍(`CORE1_DISP_PERIOD_MS = 5`)→ 注释说 20ms, 实际 100ms。
  这一条让"数字跳"和"代码意图"完全脱钩, 也说明**不能再用"数拍"当时间**。

### 为什么一次改得这么大
大字原来是一个整标签: 改一位也要重刷 110x44 = 9.7KB, 25MHz 下 **3.1ms**; 而面板扫过这
44 行只要 **2.6ms** —— 写的时间比面板扫过它的时间还长, 几乎必然被撕。

### 还有一笔白白浪费的带宽
`lv_obj_set_style_text_color(lbl_fb, ...)` 在每个分支里**每拍无条件**调用一次, 而 LVGL
不去重 → 状态行被标脏, 每 10ms 就被重刷一遍(105x17, 约 1.1ms)。模拟里这一项占掉
**847ms/8s ≈ 10% 的 SPI 时间**, 是"刷屏很慢"的最大单项。它内容没变所以看不出来,
但它把显示任务和 SPI 都占着, 挤掉的是真正需要刷新的东西。

## 3. 物理约束(必须说清楚)

ILI9341 这一类的屏**没有帧缓冲双缓冲**, 也没有把 TE(tearing effect)引脚引到 J10 上。
只要在面板扫过某区域的过程中改 GRAM, 就一定会有一次"新旧混在一帧里"。所以目标不是
"绝对不撕", 而是:
1. **少改**: 数字稳定下来, 大部分刷新是"写同样的内容"(相同内容被撕也看不出来);
2. **改得短**: 一次只写变的那一位, 让写入时间 < 面板扫过这条带的时间;
3. **别白刷**: 内容没变就一个字节都别发。

## 4. 改动清单(只动 `src/lcd/lcd_ui.c`, 控制环零改动)

| 改动 | 为什么 |
|------|--------|
| 节流改用 `lv_tick_get()` 真时间(`UI_REFRESH_MS = 20`) | 修掉上面那个 1ms/5ms 的时间基准 bug, "20ms" 就是 20ms |
| 大字拆成 **4 个定宽数字位**(`UI_RPM_CELLS`×`UI_RPM_CELL_W = 28px`, 每位 `LV_TEXT_ALIGN_RIGHT`) | 改一位只重刷 28x44 = 2.5KB(**0.79ms**), 明显短于面板扫这条带的 2.6ms; 整组仍是左对齐从 x=12 开始, 与原来看起来一样(`layout_check.py` 证明只有大字区变了像素)。**位宽必须 ≥ 最宽数字的步进**: 实测 montserrat_40 里 `0`/`4` 是 27px, 所以取 28 —— 取小了会被 LVGL 换行/裁掉, 那本身就会变成"数字乱码" |
| 显示值加 **EMA 滤波**(`UI_RPM_FILTER_MS = 250ms`) | 屏上该显示"读数"而不是瞬时采样: 末位噪声被平均掉, 数字就稳了; 真变化 0.3s 内跟上 |
| **死区 + 限速 + 心跳**: 差 ≥`UI_RPM_DEADBAND`(3RPM) 才改, 两次改写至少隔 `UI_RPM_MIN_GAP_MS`(100ms), 另有 `UI_RPM_FORCE_MS`(1s) 兜底 | 稳态时每秒只改 1~2 次; 加速时也不会几十次/秒地刷 |
| 颜色**只在变化时写**(`ui_text_color()`, 大字和状态行都缓存) | LVGL 不去重, 原来每次调用都标脏; 这一条砍掉约 10% 的 SPI 占用 |
| 上电显式写一次大字(`ui_rpm_commit`) | 滤波 + 死区之后, "转速本来就是 0"会永远不满足改屏条件, 大字会空着 |

调参入口全部是文件顶部的宏(`UI_RPM_*`), 想更"跟手"就把 `UI_RPM_FILTER_MS` 调小、
`UI_RPM_DEADBAND` 调到 1~2; 想更"稳"就反过来。**注意**: 这几条只影响显示。

## 5. 改后的模拟结果(8 秒, 两套策略同一组转速信号)

| 指标 | 改前 | 改后 | 变化 |
|------|------|------|------|
| 大字改写次数 | 7.5 次/秒 | 1.8 次/秒 | **-76%** |
| 屏上数字可见变化 | 12.9 次/秒 (轴 y) / 13.5 (轴 x) | 4.0 / 4.5 次/秒 | **-69% / -67%** |
| 撕裂段数 | 44 段 (轴 y) / 39 段 (轴 x) | 14 段 / 13 段 | **-68% / -67%** |
| 撕裂总时长 | 96 ms (1.45%) / 246 ms (3.71%) | 94 ms (1.35%) / 98 ms (1.40%) | 轴 y 基本持平 / 轴 x **-60%** |
| 数字带来的 SPI 时间 | 113.7 ms / 8s | 21.3 ms / 8s | **-81%** |
| 状态行白刷的 SPI 时间 | 847.3 ms / 8s | 0 | **-100%** |

**为什么"撕裂总时长"没有同比例下降(轴 y)**: 撕裂是"面板正扫到数字那几行时我们在写"
造成的, 每次被撕开的时间由面板自己的一帧长度决定(最多 ~14ms), 与写多长没有线性关系 ——
写短了只是"被扫到的概率"变小(3.05ms -> 0.79ms), 事件少了 3 倍, 但每次都还是要等面板
扫完这一遍才恢复。真正变好的是这三件事:
1. **数字稳了**: 改写率 7.5 -> 1.8 次/秒, 屏上数字变化 12.9 -> 4.0 次/秒 —— 眼睛能读了
   (改前每秒变十几次 + 每次都被撕, 这才是"乱码"的主因);
2. **每次撕的范围小了**: 改前一次写整条 110px 宽的数字带(整屏数字一起花); 改后一次只写
   *变的那一位*(28px), 行级裂缝落在这 28px 里, 其它位不受影响(同一拍里改两位时,
   这两位之间会有一次"一位已更新、另一位还没"的中间态, 到面板下一遍扫描就一致了);
3. **不再白刷**: 状态行那 847ms/8s(约 10% 的 SPI 时间)拿回来了。

要再往下压只剩两条路: 提 SPI 时钟(写更短 -> 被扫到的概率更低), 或者把面板的 TE 信号
接出来做同步(硬件改动)。见第 7 节。

整屏对照图(模拟器按上面两套策略真正"显示"出来的画面, 已放大 3 倍):
`tools/lcd_sim/out/before_torn_axisy_x3.png`(改前, 抓的是被撕开那一瞬)、
`after_clean_axisy_x3.png`(改后)。`axisx` 那两张是"面板沿 x 扫"的另一种几何。

## 6. 上板验证

构建(两个核都要):

```
D:\sdk_env\tools\ninja\ninja.exe -C build\core1      # 显示核(core1)
D:\sdk_env\tools\ninja\ninja.exe -C build            # 控制核(core0, 会把 core1 镜像嵌进去)
```

> 只编 `src/lcd/*` 时注意: 这些文件**只**编进 core1 的镜像, 用 `tools/_cc.py` 验证会得到
> "0 个文件/全部通过"的假结果。为此加了 `tools/_cc_core1.py`(按 `build/core1/compile_commands.json` 编)。

观察点:
1. 电机稳速(比如 300RPM)时, 大字应是**稳定可读**的数字, 每秒只跳 1~2 次, 不再"糊成一团";
2. 拖动滑条/加速时数字按 3RPM 的步子连续变, 不会闪;
3. 5 秒日志里 `LCD 5s: ... busy/tmo/abort` 仍应恒为 0(如果非 0, 那是另一条路 —— 传输侧,
   见 `LCD_DISPLAY_FIX_REPORT.md` 的实验 1);
4. 想看"改前/改后"的对比, 把 `UI_RPM_FILTER_MS` 改成 0、`UI_RPM_DEADBAND` 改成 1、
   `UI_RPM_MIN_GAP_MS` 改成 0、并把 `UI_RPM_CELLS` 的用法退回单标签, 就能复现原来那种
   "每 100ms 跳一次 + 被撕开"的画风。

## 7. 没做但值得做的事(按性价比排)

1. **SPI 时钟**: 现在目标 32MHz, 实际由分频选到 25 或 32MHz。每提 28%, 一次写入的时间
   就少 22%, 撕裂概率同比例下降 —— 代价是 ILI9341 写周期手册值只有 10MHz(已经在超频跑),
   再提要自己评估稳定性。
2. **SPI1 TX DMA 已经是现成的**(`LCDHw.c` 里那套), 它解决的是"CPU 被抽走"而不是撕裂;
   如果要进一步降 CPU 占用可以启用, 对撕裂没有直接帮助。
3. **TE 同步**: 换一块把 TE 引出来的屏模块, 或者在 J10 上飞线接 TE(需要硬件改动),
   才能做到真正的"零撕裂"。
4. `lcd_ui.c` 里"目标转速/回读行"目前只在内容变化时写, 已经是去重过的; 如果以后加了
   常变的元素(动画/进度条), 记得同样做去重 + 限速, 否则会重犯这次的问题。
